# obsgod Repository Audit

**Date:** 2026-06-08  
**Auditor:** GitHub Copilot  
**Repository:** szmyty/obsgod

## Executive Summary

`obsgod` is a Go command-line tool for remotely controlling OBS Studio via the obs-websocket plugin. The repository is a fork of [`muesli/obs-cli`](https://github.com/muesli/obs-cli) and retains the upstream identity throughout most of its configuration, documentation, and module declarations. The codebase is functional but requires modernization across dependency management, CI/CD configuration, code quality, security posture, and repository identity alignment.

## 2. Dependency Analysis

### Direct Dependencies (`go.mod`)

| Dependency | Version | Notes |
|------------|---------|-------|
| `github.com/andreykaipov/goobs` | `v0.8.0` | Targets obs-websocket **v4.x**. OBS Studio 28+ ships obs-websocket **v5** built-in; v4 requires the legacy plugin. A migration to goobs v1.x (obs-websocket v5) is needed for modern OBS. |
| `github.com/muesli/coral` | `v1.0.0` | A fork of [spf13/cobra](https://github.com/spf13/cobra). Coral has seen no releases since 2022. The upstream cobra library is actively maintained and should be considered. |
| `github.com/dustin/go-humanize` | `v1.0.1` | Up-to-date, no issues. |

### Indirect Dependencies (`go.sum`)

| Dependency | Version | Notes |
|------------|---------|-------|
| `github.com/gorilla/websocket` | `v1.4.2` | Transitive via goobs. v1.4.2 is old; [CVE-2020-27813](https://github.com/advisories/GHSA-jf24-p9p9-4rjh) (DoS) was fixed in v1.4.3. Version is inherited from goobs and will be resolved by upgrading goobs. |
| `github.com/nu7hatch/gouuid` | old | Transitive via goobs. |

### Go Toolchain

The `go.mod` specifies `go 1.13`. The current stable Go release is 1.22.x. The CI matrix tests `~1.12` (an old patch release) and `^1` (latest). The minimum Go version should be raised to at least `1.21` (the oldest supported release).

**Recommendation:** Upgrade all direct dependencies, especially `goobs` to v1.x for obs-websocket v5 compatibility. Raise the `go` directive in `go.mod` to `1.21` or higher. Consider replacing `coral` with upstream `cobra`.

## 3. CI/CD Configuration

### GitHub Actions Workflows

#### `build.yml`
- Uses `actions/setup-go@v3` and `actions/checkout@v3` — these are outdated; `@v4` is current.
- Tests against `~1.12` Go version, which is well beyond end-of-life.
- `GO111MODULE=on` is a legacy env var, unnecessary in modern Go.

#### `lint.yml`
- Uses `golangci/golangci-lint-action@v3` — v6 is current.
- Passes `--issues-exit-code=0` which silently ignores lint failures; should be removed to enforce linting.
- `only-new-issues: true` is appropriate for a PR workflow.

#### `coverage.yml`
- Uses `GO111MODULE=off go get github.com/mattn/goveralls` — `GO111MODULE=off` with `go get` is a legacy pattern.
- Should use `go install` instead.
- Uses deprecated `goveralls` pattern; consider using [coveralls-github-action](https://github.com/coverallsapp/github-action) directly.

#### `goreleaser.yml`
- Uses `goreleaser/goreleaser-action@v4` — v6 is current.
- Passes `--rm-dist` flag which was removed in goreleaser v2; replaced by `--clean`.
- The goreleaser config `.goreleaser.yml` uses v1 schema (no `version:` key), which requires `--deprecated` flag in goreleaser v2.

### `.goreleaser.yml`
- `replacements` under `archives` is deprecated since goreleaser v1.5.0; use `name_template` instead.
- `ldflags` references `-X main.Version={{ .Version }}` and `-X main.CommitSHA={{ .Commit }}` but `main.go` declares `version string` only (no `CommitSHA` variable); ldflags are referencing a non-existent variable.
- `signs` block references signing without configuring a key; will fail in non-release contexts.
- `brews` section references a tap that belongs to the upstream author.

**Recommendation:** Update all action versions to `@v4`+, update goreleaser config to v2 schema, fix ldflags, and remove or update the brews/tap configuration.

## 4. Linter Configuration (`.golangci.yml`)

Several linters listed in `.golangci.yml` have been removed from golangci-lint in recent versions:

| Linter | Status |
|--------|--------|
| `ifshort` | **Removed** in golangci-lint v1.48+ |
| `exportloopref` | **Removed** in golangci-lint v1.61+ (Go 1.22 fixed loop variable scoping) |
| `godox` | Available, but `TODO`/`FIXME` markers exist in source code that would trigger it |

Additionally, many recommended linters are absent:
- `errcheck` — unchecked errors exist in the codebase
- `govet` — static analysis
- `staticcheck` — comprehensive static analysis
- `noctx` — HTTP requests without context
- `gocritic` — style issues

**Recommendation:** Update `.golangci.yml` to remove deprecated linters, add `errcheck`, `govet`, and `staticcheck`, and enforce linting in CI (remove `--issues-exit-code=0`).

## 5. Code Quality

### Dead Code

**`sources.go` (lines 40–54):** A large commented-out block remains from a previous implementation using a different OBS websocket library. It includes an incomplete import (`spew.Dump`) and serves no documentation purpose.

```go
// sources.go:40-54
/*
    {
        req := obsws.NewGetSourcesListRequest()
        resp, err := req.SendReceive(client)
        ...
        spew.Dump(v)
        ...
    }
*/
```

**Recommendation:** Remove dead commented-out code.

### Typo in Function Name

**`virtualcam.go` (line 51):** The function `starStopVirtualCam` is missing the `t` in `start`.

```go
func starStopVirtualCam() error {  // should be starTStopVirtualCam or startStopVirtualCam
```

**Recommendation:** Rename to `startStopVirtualCam` for consistency with the pattern used in `stream.go` (`startStopStream`) and `recording.go` (`startStopRecording`).

### Unexported Exported-Style Function in `main` Package

**`studiomode.go` (line 71):** `IsStudioModeEnabled` uses exported (PascalCase) naming in a `main` package. While not harmful (the `main` package cannot be imported), it is inconsistent with all other unexported helper functions in the codebase.

**Recommendation:** Rename to `isStudioModeEnabled` for consistency.

### Unchecked Errors

The `main()` function silences the `client.Disconnect()` error:

```go
_ = client.Disconnect()
```

While acceptable at shutdown, this pattern should be documented.

### Missing Tests

The repository has **zero test files**. Given that the CLI makes network calls to OBS, integration tests require a live OBS instance, but unit tests for helper functions (e.g., `fmtDuration`, argument validation, command registration) are feasible without a running OBS.

**Recommendation:** Add unit tests for pure functions and command argument validation. Consider integration test scaffolding with a mock websocket server.

## 6. Security

### Password Exposure

The OBS connection password is passed as a CLI flag (`--password`):

```go
rootCmd.PersistentFlags().StringVar(&password, "password", "", "password for connection")
```

Command-line arguments are visible in the process list (`ps aux`), shell history, and system logs.

**Recommendation:** Support reading the password from an environment variable (e.g., `OBS_PASSWORD`) or a credentials file as an alternative to the `--password` flag.

### No Input Validation

Scene names, source names, and other user-provided arguments are passed directly to the OBS websocket API without sanitization. While OBS handles this server-side, the CLI provides no client-side feedback for obviously invalid inputs (e.g., empty strings).

## 7. Architecture & Design

### Single `main` Package

The entire codebase is a single `main` package with no library separation. While acceptable for a small CLI tool, extracting the OBS client interaction into a separate internal package (e.g., `internal/obs`) would improve testability and maintainability.

### Global State

The `client` and connection parameters (`host`, `password`, `port`) are global variables. This design makes concurrent use and testing difficult.

### `coral.OnInitialize` for Connection

Using `coral.OnInitialize(connectOBS)` means a connection to OBS is attempted for **every command invocation**, including `--help`. If OBS is not running, help commands fail:

```
error: dial tcp: connect: connection refused
```

**Recommendation:** Lazy-initialize the connection, or only connect when a command that requires it is actually run (using `PersistentPreRunE`).

## 9. obs-websocket Compatibility

The most significant modernization gap is obs-websocket compatibility:

| Component | Version | Notes |
|-----------|---------|-------|
| `goobs` dependency | `v0.8.0` | obs-websocket v4.x API |
| OBS Studio 28+ | Built-in obs-websocket v5 | Protocol incompatible with v4 |

Users on OBS Studio 28 or later must install the legacy obs-websocket v4 plugin separately, which is no longer maintained. Migration to `goobs v1.x` (obs-websocket v5) is the highest-impact modernization action.
